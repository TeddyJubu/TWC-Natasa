# Agents

- All design-system source (theme CSS, components, helpers) lives in `src/design-system/` and is re-exported from `src/index.ts` — attach copies only that subtree, so nothing there may import from outside it. App code imports it only via `@/index`; ESLint `no-restricted-imports` enforces both directions.
- Showcase pages (`/colors`, `/typography`, `/components`) live in `src/routes/` and are the only routes on the `Shell` toolbar from `src/showcase/` (showcase-only helpers, excluded via `.dsignore`); they carry `noindex` and are disallowed in `public/robots.txt`. Live pages use `AppPage`, `AppNav` and `AppFooter` from `src/app/layout/AppLayout.tsx` — keeps the design-system toolbar off the live site and out of search, while the showcase stays preview-only and never re-exported.
- Public pages are the scrapbook site from the design canvas: the prop-less `AppNav` (About · Members · Gatherings · logo · Neighborhoods · FAQ · Sign in · Join us, a popover menu below lg) and lilac `AppFooter`, the `twc-*` classes in `src/app/twc.css` (the canvas's design system ported onto the `sb-*` tokens and self-hosted fonts, in `@layer components` so utilities win) and `Icon`/`Scallop`/`TwcRibbon` from `src/app/layout/twc.tsx`. Headlines are sentence-case Gilda Display, small blue text uses `sb-blue-ink` (`sb-blue` fails AA below 24px), and a `[BRACKETED]` fact on a board is never invented — the element is dropped instead. App-only, never re-exported — keeps every public page on one visual language without loading fonts from a third party.
- Tokens are CSS variables mapped through `@theme inline` in `theme.css` — keeps light/dark switching to a single `.dark` class.
- Form primitives use editorial and boxed variants from one shared family — keeps long applications expressive and compact forms consistent.
- Motion uses shared CSS timing tokens and reduced-motion fallbacks — keeps interactions consistent and accessible without adding a runtime dependency.
- Long membership forms compose reusable field, choice, notice, progress, section, and action primitives — keeps dense applications consistent and accessible.
- The uploaded constellation artwork is the canonical logo and `ConstellationLogo` owns its fixed color variants, each with 128w/256w lossless WebP downscales in its `srcset` (`logo-sources.ts`; a caller that sets its own width passes `sizes`) — preserves the original geometry across every brand context without shipping the 471px PNG to a 28px mark.
- Immersive image strips use the self-contained OGL circular gallery with a static reduced-motion fallback; `CurvedGallery` lazy-loads the engine and the barrel exports only its props type, so OGL never ships in the every-page chunk (`src/app/code-split.test.ts`) — preserves the editorial arc while remaining accessible and attach-safe.
- Decorative pointer motion uses the self-contained star `ImageTrail` (glittering sparkles) on public pages only (internal pages pass `trail={false}` to `AppPage`), disabled for touch and reduced motion — keeps the playful flourish accessible and attach-safe.
- Clicking an enabled button in the app shell scatters a tiny star burst (`useButtonSparkles` in `src/app/layout/sparkles.ts`, `.twc-spark` in `twc.css`): `aria-hidden`, no pointer events, gone in 0.7 s, none under reduced motion — click feedback without a library or an inline-style CSP exception.
- Motion that starts on its own either stops within 5 s (`CurvedLoop`) or has a pause control (`Ribbon`) — WCAG 2.2.2, even when the motion is decorative and `aria-hidden`.
- Catalogue cards open details through `MemberCard`'s `onOpen` and one `MemberDialog` (a native modal `<dialog>`) per page; members without a portrait get the card's initials mat, never a stand-in photo — keeps cards honest and the dialog accessible without a dialog library.
- Demo member profiles live in `src/showcase/demo-members.ts` (with their portraits in `src/showcase/assets/`), outside the design system and the public barrel; only `MemberProfile` is type-exported with `MemberCard` — keeps the reusable API typed without pulling sample portraits into consumer bundles.
- Design rules (tokens, type, the `--hood` inline-style exception) live in `DESIGN.md` at the repo root.
- Member accounts use Better Auth on the app's SQLite database (`src/server/auth.server.ts`, served at `/api/auth/*`): email + password with required verification, plus Google only when `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are set (the button shows when `VITE_GOOGLE_AUTH === "true"`); ids are UUIDs. Membership status, catalogue number, member-since and roles are admin-only: members can never self-approve. An admin's direct approve/decline/undo-decline also updates the newest application (0004 behaviour).
- All data access is a TanStack Start server function in `src/features/*/fns.ts`; its handler lazy-imports the feature's `*.server.ts` and runs it through `serve()` (`src/server/context.server.ts`), whose domain code starts with `requireSession`/`requireMember`/`requireAdmin` from `src/server/guard.ts` — that is the security boundary (the old RLS), checked by `src/server/policy.test.ts`. The nine endpoints that take a body (`/api/images`, `/api/feed`, `/api/neighborhood-logos`, `/api/applications`, `/api/contact`, `/api/partnerships`, `/api/review`, `/api/spotlight`, `/api/forms/<slug>`) are server routes instead, so the size (Content-Length) and the caller are checked before the body is read; applications, contact messages and partnership inquiries are each limited to 5 per client IP per 10 minutes, member reviews and Spotlight answers to 10, custom-form answers to 10 per client IP per form, newsfeed posts to 10 per member per 10 minutes (their own `rateLimit()` from `src/server/request.ts`; `clientIp()`: `cf-connecting-ip`, then the first `x-forwarded-for`). The CSRF middleware covers them only because each is listed in `API_ROUTES` in `src/start.ts` — a new body-taking route must be added there, with a test. The browser never touches the database; client code imports only `fns.ts`, `postApi`, query/mutation modules and types.
- Code that needs a secret reads `process.env` only in server-only modules (`src/server/`, `*.server.ts`). Server env lives in the server's environment or the gitignored `.env.local`; tracked `.env` holds only `VITE_` values (`src/app/secrets.test.ts`). Every email goes through `sendEmail()` in `src/server/email.ts`, with links at `APP_URL`.
- The database is SQLite (`node:sqlite`) at `${DATA_DIR}/twc.db`; migrations are hand-written `db/migrations/NNNN_name.sql`, applied in order at startup via `PRAGMA user_version`. Never edit an applied migration; add the next one, with tests.
- Uploads live under `${DATA_DIR}/uploads/` and are served only by `/media/*` (`src/server/media.ts`): magic-byte checked on upload, at most 2560px a side (feed 4096px, read from the header by `imageSize`), stored without metadata except a JPEG's Exif Orientation (`image-meta.ts`), after the browser has shrunk and turned each one upright (`resizeImage` in `src/app/resize-image.ts`: portraits 1600px, logos 512px keeping transparency, feed photos 2048px; WebP, else JPEG/PNG; the original when it can't), visibility from the old storage rules, 404 for anything not visible or outside a bucket; a weak ETag/Last-Modified answers revalidation with a 304 only after that visibility check, and only files anyone may see are `public` in Cache-Control.
- Live pages put their content in one `<main id="main" tabIndex={-1}>` after `AppNav` (`AppPage` adds the skip link), and the root's `useRouteFocus` focuses its `h1` after each navigation — keeps landmarks and route announcements consistent for screen readers.
- Internal (signed-in) pages — `/account`, `/admin`, `/admin/forms` and any future page under `_authenticated` — share one design system, airmail (DESIGN.md "Internal tools"): `.air` next to `app-ground` on the page root, the `air-*` tokens in `theme.css` (colour, `rounded-air-*`, `shadow-air-*`; `.air` re-points the `app-*`, `ink` and `sb-*` tokens at them so older utilities follow), the `air-*` classes in `twc.css`, and the kit in `src/app/layout/app-ui.tsx` (`Letter`, `Card` = a letter of ruled rows, `Row`, `Field`, `Chip`, `Toggle`, `EditButton`, `InlineError`, `EmptySlot`, `TicketDate`) with the control classes in `app-classes.ts` and the icons in `icons.tsx`. The admin pages use `AppShell` (`src/app/layout/AppShell.tsx`: a paper sidebar, a modal `<dialog>` drawer below lg) plus a sticky paper `TopBar`; `/account` uses `AirShell`. Public pages never use them. The sidebar's groups (My Account, then Admin and Forms for admins only — UX only, the guards decide) link `page#card`; a card on the current page is an in-page anchor with `aria-current` while in view. Each page passes its `page` and `admin` and keeps `AppPage`'s skip link and one `<main id="main">`; its `h1` is the top bar title — keeps every internal screen one consistent, accessible tool.
- `/directory` is the signed-in member directory on airmail (DESIGN.md "Member directory"): `AirShell page="/directory"`, a stamp sheet (`air-sheet`/`air-slot`, twelve a sheet) whose stamps tear out onto a pass of only published facts; members and admins read `directoryQuery`, others `publicProfilesQuery`; `noindex`. Public `/members` stays on the scrapbook site — keeps the internal design system off public pages.
- `/account` is the airmail member profile (DESIGN.md "Member profile"): `AirShell` (top bar; her name and avatar open the account menu of `shell-nav.ts` sections on hover, click or Enter, with Admin for admins; no sidebar) on the internal design system above. Gilda Display (headings, weight 400 only) and Geist (body) are the shared faces; IBM Plex Mono is self-hosted for its labels. Her name is the `h1`; cards edit into one draft that Save sends as only the changed fields; "View public card" opens her member pass (`MemberPass.tsx`, portrait/landscape) whose colour swatches save `card_color` (migration 0012, `CARD_COLORS` in `card-colors.ts`, checked by the server and the database) on the spot; pass and stamp details show only facts she or an admin set; "Where you belong" (under the cover) pins her neighborhood's centre from `places.ts`, never an address, and drops any row it has no fact for — keeps the member's own page a keepsake without forking the controls.
- Contrast is tested, not eyeballed: `src/app/contrast.test.tsx` checks token pairs parsed from `theme.css` (including every app-shell pair), so a token or text-colour change that drops below WCAG AA fails the suite.
- `src/start.ts` owns the request middleware: security headers (`src/app/security-headers.ts`: an enforced CSP from `contentSecurityPolicy()`, same-origin except `https://doop.design` in `script-src` and `connect-src` for the design-sync script on `/f/<slug>`, and `https://tiles.openfreemap.org` in `connect-src` only for the `/account` map's tiles (MapLibre's worker is a same-origin file via `setWorkerUrl`) — `img-src 'self' data: blob:`, `frame-ancestors 'self'`, `object-src 'none'`; a new external origin goes there, with a test; `X-Robots-Tag: noindex` on the client-rendered signed-in pages `/account`, `/directory`, `/feed`, `/admin*`) plus Start's CSRF check restated, because a start instance replaces Start's default middleware — never drop `csrfMiddleware`. `server.mjs` puts the same headers on static files, and adds the edge helpers of `src/server/edge.ts`: a 308 off a trailing slash (GET/HEAD, not `/api` or `/media`), a year's `immutable` caching for hashed `/assets/*`, and gzip for the app's HTML/JSON/XML.
- Public reads of member data return only what `publicProfiles()` returns (approved + directory-visible + public profile): `/members/:slug` (name + catalogue number; the number alone resolves, a stale name redirects) is a 404 for anyone else signed out, and approved members also see directory-visible members there under `noindex`. `/`, `/members`, `/gatherings` and `/neighborhoods/:slug` put those public cards (and the public calendar) in the server's HTML through their route loaders (`loadPublicProfiles`/`loadPublicEvents`, seeding the page's query as `initialData`); members and admins still switch to `directoryQuery` on the client. `/sitemap.xml` is a server route (`src/server/sitemap.ts`) listing `INDEXED` from `src/app/seo.ts`, active neighborhoods and public member pages. `public/robots.txt` is one group naming `*` and each search/answer crawler (so all share its Disallows: showcase, `/review`, `/spotlight`, `/api/`, `/_serverFn/`, the private `avatars`/`feed` media buckets — never the signed-in pages, whose `X-Robots-Tag: noindex` a crawler must be able to fetch); `public/llms.txt` and `llms-full.txt` state only facts from the public pages' copy and link only `INDEXED` pages, with the FAQ word for word from `faq.tsx` (`src/app/llms-txt.test.ts`) — keeps private members out of search the moment they turn their page off.
- Contact messages and partnership inquiries are stored in `inbox_messages` (migration 0002) and then emailed to every admin (`receiveMessage` in `src/features/contact/contact.server.ts`): consent is required, a filled `honeypot` gets the same success with nothing stored or sent, and the `/admin` Inbox card lists `new` ones for archiving (`requireAdmin`) — keeps every message even when mail fails.
- Personal member review links (`src/features/member-links/`, migration 0003): an admin mints one for an approved member in the `/admin` members table, and the URL is shown once; only the token's SHA-256 is stored. `/review?t=` needs no sign-in, gives every bad, used or expired token the same 404, and stores the answers in `member_reviews` in the same transaction that marks the link used. Answers never change the profile; a person applies them from the "Member reviews" card. Keeps a leaked database or backup from opening anyone's review, and keeps members from approving or editing themselves through a link.
- Weekly Spotlight (migration 0008) reuses member links with `purpose = 'spotlight'` (the same mint/revoke/state functions, `purpose` in their input; every token lookup filters on purpose, so neither kind opens the other's form): `/admin` "Invite to Spotlight" shows the URL once, `/spotlight?t=` needs no sign-in and gives every bad token one 404, and `POST /api/spotlight` stores `spotlight_answers` (keyed by the old Google Form column names) in the same transaction that marks the link used. Imported history (`scripts/import-legacy.ts`, no link, old ids kept) shares the table; admins read both in the "Spotlight answers" card. Keeps one hashed-link mechanism for every personal link and the old answers next to the new ones.
- Newsletter opt-ins reach Beehiiv only through `subscribeIfConsented()` (`src/server/beehiiv.ts`): an explicit `true`, never an address already in `newsletter_subscribers` (the imported list has `consent` null), no reactivation; applications need `newsletter` **and** `emailConsent`. Admin alerts (contact, partnership, new application, member review, Spotlight answer) go through `notifyAdmins()` (`src/server/notify.ts`) and never fail the request — keeps a leaked or replayed row from re-subscribing anyone and a mail outage from losing a stored message.
- Custom forms (`src/features/forms/`, migration 0005) are rows, not files: `/f/<slug>` shows an open form (or its closed words), `/f/<slug>/thanks` its thank-you, and an old name 301s to the current one; answers go to `POST /api/forms/<slug>` and only the form's own question keys are stored. Definitions are written only through `saveForm` (questions checked by `checkQuestions`); intro/thank-you/closed words are plain text, never HTML. Admins open/close forms, edit the closed message, read answers and download per-form CSV in `/admin/forms` — the admin Forms section: every form as a card, "Your forms" (these, plus a New form card: name and web address only, created closed with name + email questions) then "Built-in forms" (the newsletter is a note, not a card), the whole card opening its own edit page at `/admin/forms/<id>`; a custom form's card also has a trash button that confirms (naming its answer count) and then `deleteAdminForm` removes the form with its answers and old names in one transaction — built-in forms are code and have none. A custom form's page has a summary ticket, then Answers / Questions / Settings tabs (`?tab=`, all mounted, only hidden): Questions is the form on a paper sheet with its name, intro, questions and thank-you edited in place; the link, one-per-email, open/closed and the closed message live only on Settings, and every save sends the fields it doesn't own from the server's latest row, so the question editor can never reopen a form (question keys and choice values are made once in `form-draft.ts`, never shown or changed) (`setFormOpen` / `formResponsesCsv`, `requireAdmin`). Demo forms live in `src/features/forms/fixtures.ts` (`scripts/seed-forms.ts` for local runs); the CRM's live forms and old answers come in once through `scripts/import-forms.ts` (Node; definitions from the CRM database, never choices from published HTML) — keeps the apex's `/f/*` links working after cutover without porting the old page splicer.
- Membership join/review open-close (`src/features/forms-state/`, migration 0010): `forms_state` rows for `application` (`/join`) and `review` (`/review`) only — Spotlight stays always-on. Admins toggle from the join/review form's own edit page, `/admin/forms/application` or `/admin/forms/review` (`setMembershipFormOpen`, `requireAdmin`); closed pages show closed words on 200 (valid review links still resolve); closed POSTs refuse with 410 and store nothing. A missing row means open. No Classic `forms_state.json`.
- `/admin` CRM parity (phase 1): one search box filters the Inbox, Applications and Members cards client-side (`matchesSearch`), private admin notes live in `admin_notes` (migration 0006, one application **or** member per note, add/delete only), and "Download CSV" comes from the `adminCsv` server function (`toCsv`: BOM, CRLF, formula guard) saved through a blob link — keeps exports and notes behind `requireAdmin` without a new body-taking route. Phase 2: Status (both cards) and Neighborhood (members) filters AND with that search; each members row's Details shows her newest application (`newestByUser`, origin via `applicationOrigin`) and sets her neighborhood through `setMemberNeighborhood` (a listed one or none; the application's answer never changes); `formatAnswers` hides the CRM's hidden keys and the import's `legacy` record. Phase 3: pending applications carry a read-time `duplicate` flag (`duplicatesOf`: same email as an approved or imported member, or repeated among pending ones — never stored, never merged); Details opens on newsletter / application-count / member-since chips; every approve, decline, note and neighborhood change appends to `admin_actions` (migration 0007, update/delete triggers abort, ids only, no FKs) in the same transaction, shown in the "Admin activity" card. Phase 4: undo-decline + confirm on approve/decline; three statuses only. Phase 5: logged actions outside the app (`0009_logged_actions.sql`, soft-remove + append-only event log; not `admin_actions`) on application rows and member Details; read-only Newsletter subscribers card (page search filters it; no Beehiiv write).
- Built-in form wording (`src/features/form-copy/`, migration 0011): the code keeps every default text; `form_copy` rows (form + the default text as `original`) replace one text on `/join`, `/review`, `/contact` and `/partnerships`, edited on that form's `/admin/forms/<id>` page (`saveFormCopy`, `requireAdmin`; blank or the default deletes the row). Only texts in `manifest.ts` are read or stored (`form-copy.test.tsx` checks each against the page source); pages pass them through `t()` from `useCopy()` inside `FormCopyProvider`. Consent statements, answer choices, notices and legal text are never editable, and the question set stays fixed so applications, the Inbox and newsletter consent keep working — keeps wording an admin task without a second form engine.
- `/feed` is the members' newsfeed on airmail (DESIGN.md "Newsfeed", migration 0013, `src/features/feed/`): `AirShell page="/feed"`, linked as "Newsfeed" in the account menu; approved members and admins read, post (`POST /api/feed`: words and/or up to four photos, each with an optional description that becomes its alt text), love and reply through `requireMember`; a member deletes her own posts and replies, an admin anyone's; no edit. Photos live in the private `feed` media bucket (`<author id>/<post id>-<n>.<ext>`, metadata stripped), served only while both the reader and the author are approved or admins; a member who is no longer approved drops out of the feed with her posts, loves and replies. Author portraits follow the avatar rule (`canSeeAvatarFolder`), so a member not listed in the directory posts under her initials. Bodies are plain text, never HTML; the kinds (update, ask, offer, gathering) are tags only — keeps the community's talk behind sign-in with the same guards, buckets and design system as the rest of the internal tools.
- The whole app is a private preview while `SITE_PIN` is set in the server's environment: `pinGate` (`src/server/site-pin.ts`) runs first in `server.mjs`, before static files and the app, so every page, `/api`, `/media` and asset needs the PIN cookie (a SHA-256 of the PIN, HttpOnly, 30 days) or gets the self-contained PIN page, which returns to the requested path (same-site paths only). Open: the three icons and `/healthz` (the deploy's health check; it opens the database). Wrong PINs are limited to 10 per client IP per 10 minutes. The PIN is never in the repository (it is public) — only in `/etc/twc-natasa/app.env`. The favicon everywhere is the constellation star on a white tile (`public/favicon.ico`, `favicon.png`, `apple-touch-icon.png`, linked from `__root.tsx`) — keeps an unfinished site out of sight without touching the shared Caddyfile.
