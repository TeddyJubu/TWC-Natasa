## 1. `apply_site_forms.py` (website forms into static pages)

- **OPS-405** (D-13) **What it does and which pages it owns.** For three website forms it reads `data/crm/published/<kind>.json` and swaps the form's HTML into a static page: `contact` into `contact.html`, `partnership` into `partnerships.html`, `newsletter` into `index.html` (`apply_site_forms.py:53`). **`index.html` is also the apex coming-soon page that BRIEF decision 1 keeps**, so the newsletter form on that page stays wired to this chain (CRM publish, this job, forms service, Beehiiv; OPS-256) until the rebuild replaces it. A kind with no file is logged "nothing published yet" and skipped (`:379-382`). **MECHANISM** for the splice; the three forms' content and behaviour must survive.
- **OPS-406** (D-14) **Markers and first run.** The form sits between `<!-- nbwc:form-<kind>:start -->` and `<!-- nbwc:form-<kind>:end -->` (`:265-266`). On the first run, when the markers are absent, it wraps today's hand-written `<form name="<kind>">` (exactly one must exist) through its closing `</form>` (`:346-351`). Broken or duplicated markers raise `Refused("markers are broken in the page")` and leave the page alone (`:343-344`).
- **OPS-407** (D-15) **Trust boundary for published HTML.** The CRM is treated as untrusted: at most 100,000 characters (`:54`), ASCII only ("the renderer always escapes", `:306-307`), at most one form, no `script|style|link|meta|base|iframe|frame|object|embed|template|math` tags, no `on*=` handlers, no `javascript:`, `vbscript:`, `data:text`, no comments, no `srcdoc=` or `formaction=` (`:55-62,317-319`). Byte-for-byte exceptions: the checkbox tick SVG (`:64-65`), Cloudflare's Turnstile loader once (`:69,308-310`) and the page script `/assets/form-logic.js?v=2026-11-02-w6` only as the form's last line (`:75,311-314`). Any other `<svg` is refused (`:315-316`). The form tag must be `<form name="<kind>" data-validate action="/message-sent.html|/subscribed.html"` and the markup must end with `</form>`; or it must be a closed message `<div class="notice form-closed" role="status" data-form="<kind>"` with no form (`:323-334`).
- **OPS-408** (D-16) **WebMCP, source and via fields.** A form may describe itself to AI assistants with only `toolname` and `tooldescription` on the `<form>` tag and `toolparamdescription` on inputs, selects, textareas and fieldsets; `toolautosubmit` is refused ("a form never sends itself", a person always presses Send) (`:81-85,280-298`). `form-via` and `form-src` hidden inputs must each appear at most once, exactly as written, and empty (`:85-88,269-277`). A raw `>` inside an attribute is refused (`:287-288`). The rebuilt forms need the same WebMCP attributes and the empty `form-src`/`form-via` fields, because the page script fills them from `?src=` and the assistant.
- **OPS-409** (D-17) **Logic attributes.** `data-show-if|op|value|rule`, `data-jump`, `data-total`, `data-total-of`, `data-total-live`, `data-score` and `data-save*` are accepted only on the elements the renderer puts them on, with operators from `is, is_not, includes, gt, lt, eq, contains, not_contains, before, after, answered, not_answered`, at most 20 conditions, 10 jumps, 200-character values, 20 totals, nesting depth below 2, scores matching `-?\d{1,6}(\.\d{1,2})?` (`:99-188`). A jump goes to `end` or to a step from 2 to 10 (`:171`).
- **OPS-410** (D-18) **Schedules and response limits.** If the published file has `schedule` it decides at run time which markup to show: `opens_at` in the future gives the closed message ("not_yet"), `closes_at` passed gives "ended", `max_responses` (1 to 100,000) reached gives "full" (`:214-224`). Broken values are ignored (open). `open: false` shows `html` as published; a missing `closed_html` string falls back to the form (`:251-262`). Response counting scans `data/submissions.jsonl`, matches lines by the literal text `"form": "<kind>"` (`:233`), skips tombstones (`:239`), counts spam-labelled rows too, and honours `count_from`. This literal match works only because the writer uses `json.dumps` with default separators (`submissions.py:200`); a compact writer would make every count 0 and the limit would never trigger. The page can lag by up to a minute behind the limit; the forms service enforces it exactly.
- **OPS-411** (D-19) **Write rules.** Pages are written with temp file, fsync, `chmod` and `chown` to the old page's mode and owner, then rename (`:354-367`). A kind that is refused is logged to stderr as `! <kind>: left as it is - <reason>` and the others continue (`:393-394`). Custom-form pages run inside the same lock; an exception there is caught as "custom forms: skipped" so it never blocks the website forms (`:396-399`). Thank-you pages are applied last (`:410`). CLI: `--published`, `--site`, `--submissions`, `--check` (say what would change, write nothing) (`:416-426`).
- **OPS-412** (D-20) **Failures are silent to systemd.** Every refusal goes to stderr and the process still exits 0, so the unit never shows as failed when the CRM publishes bad markup (`:393-399,425`). See OPS-523.

## 2. `thanks_pages.py`

- **OPS-413** (D-21) **Per-form thank-you pages.** For `contact`, `partnership` and `newsletter` the CRM publishes `thanks_html` inside the same `published/<kind>.json`. The job writes `site/thanks-contact.html`, `site/thanks-partnership.html`, `site/thanks-newsletter.html` as copies of `message-sent.html` or `subscribed.html` with the text swapped between `<h1 style="font-size:var(--t-hero);">` and `<div class="row" style="margin-top:var(--s-7);` (`thanks_pages.py:23-29,108-115`). The shared pages are never changed, so old addresses keep working. A file without `thanks_html` is skipped (published before F3) (`:147-148`). A file whose `kind` does not match is refused (`:145-146`).
- **OPS-414** (D-22) **Allowed thank-you markup.** At most 20,000 characters, ASCII only, no `javascript:`/`vbscript:`/`data:` URLs, no comments, no `on*=` (`:30,88-95`). Allowed tags with exact attributes only: one leading `<h1 style="font-size:var(--t-hero);">`, up to four `<p>` (class `lead` with `margin-top:var(--s-5);`, or the dim style), `<em>`, `<br>`, and `<a href>` where the href is `https://`, `mailto:` or a relative path (`:32-35,50-58,99-104`). No nesting of `h1`/`p`, no self-closing tags. Otherwise the thank-you page is left as it was.
- **OPS-415** (D-23) **Redirect target.** The forms service redirects to `/message-sent.html?form=<name>` or `/subscribed.html?form=newsletter`; Caddy swaps in the form's own page when it exists (OPS-403). Only the three known names match (`Caddyfile:130-138`). **MECHANISM**: the rebuild routes the thank-you by form id directly.

## 3. `custom_pages.py` (pages for forms made in the CRM)

- **OPS-416** (D-24) **Files written per CRM form.** `site/f/<slug>.html` (form or closed message), `site/f/<slug>/thanks.html`, `site/f/<slug>/thanks-<n>.html` (one per thank-you rule, n from 2), `site/f/<slug>/thanks-go.html` (only with a redirect), `site/f/<slug>/thanks-waitlist.html` and `full.html` (only when any choice has places), `site/f/<old slug>.html` ("This form has moved"), `site/f/<slug>/event.ics` (only with a checked event), `site/f/media/<sha256>.<ext>` and `site/forms.html` (`custom_pages.py:1-12,955-994`). Nothing is ever deleted except a form's own `event.ics` (`:21-24,1332-1341`).
- **OPS-417** (D-25) **Page template.** Each page is the site's `contact.html` with `<main id="main">` replaced; head, header, footer, styles and scripts are inherited (`:14-16,610-644`). The job rewrites `<title>`, `meta description`, `canonical`, `og:url`, `og:title`, `og:description`, and for the form page also `twitter:card=summary_large_image` and `og:site_name` (`:624-636`). It stamps `<meta name="nbwc-custom-form" content="<id>">` into the head (`:59,637`) and makes template links absolute (`:605-607`). A page may be (re)written only if missing or if it carries that form's own stamp (`:893-899,983-985`). Link-preview words come from the published `card` (title 200, description 400, single line) (`:543-549`). `SITE` is hard-coded to `https://thewomenscollective.club` for canonical URLs (`:58`, see OPS-518).
- **OPS-418** (D-26) **Validation of a published CRM form.** File named `<8 [a-z0-9]>.json`, at most 1,000,000 bytes, `kind == "custom"`, `id` equals the file name (`:556-562`). `slug` matches `[a-z0-9](?:[a-z0-9-]{0,38}[a-z0-9])?`, has no `--`, and is not in the reserved set: `about admin api apply assets contact crm directory editing events fellowship forms f index join login members message-sent new partnerships partnership privacy review robots sitemap subscribed terms thanks thank-you newsletter spotlight membership internal static 404 media beacon places` (`:41-50,563-565`). `old_slugs` follow the same rules (`:566-568`). `name` is 1 to 80 characters on one line (`:569-571`). `intro_html` must be plain `<p>` paragraphs; `thanks_html` may also contain `<span data-pipe="...">` answer placeholders (`:51-57,572-575`). The form tag must equal `<form name="custom" data-validate action="/f/<slug>" method="POST"` plus optional `enctype="multipart/form-data"`, `novalidate`, `data-layout="one"`, `data-pipe-keys="..."` (up to 20 keys), `data-save-later`, `data-save-email`, `data-places`, and the WebMCP pair; the hidden `form-id` input must equal the file's id (`:515-540`). The rebuilt `/f/<slug>` route needs the same reserved list so a form can never shadow an app route.
- **OPS-419** (D-27) **Link-name claims.** Each slug (current and old) belongs to exactly one form. If two files claim one, neither gets it ("disputed") and the page is left as it was (`:945-952`).
- **OPS-420** (D-28) **"Make it look ours" (G4).** `look` is checked on its own: `mode` is `site` (theme) or `custom`; `layout` classic or one; `accent`, `background`, `text` as `#RRGGBB`; `font` one of `site salon classic modern warm friendly`; `corners` rounded or square; `logo`/`cover` named `<64 hex>.(png|jpg|webp)`; `cover_alt` one line up to 200 (`:210-319`). WCAG 2.1 contrast must hold: text on background at least 4.5:1, button words on the accent at least 3:1, accent on background at least 3:1 (`:213,312-318`). A look that fails any check is dropped, the page is still written in the site's theme, and the reason is logged (`:582-590`). The CSS is built here with colour mixing byte-for-byte equal to `lookCss` in `crm/shared/look.ts` (`:322-358`). Four of the six font sets load a Google Fonts stylesheet (`Playfair Display`/`Source Sans 3`, `Space Grotesk`, `Fraunces`/`Work Sans`, `Nunito`/`Nunito Sans`) (`:222-233`); see OPS-519 for the CSP issue. `look_cases.json` pins this logic to the CRM (`:208`).
- **OPS-421** (D-29) **Logos and covers.** Copied to `site/f/media/<sha256>.<ext>` from `published/media/`. Each must be a regular file (opened with `O_NOFOLLOW`), at most 1 MB, whose SHA-256 equals its name, with magic bytes matching its extension (JPEG `ffd8ff`, PNG, WebP `RIFF....WEBP`) (`:384-431,468-501`). Same name means same bytes, so existing files are kept and nothing is deleted. The logo image gets `alt` = the form's name; the cover gets `cover_alt` or empty (`:371-381`).
- **OPS-422** (D-30) **Thank-you per answer.** `thanks_variants` (up to 10 rules `{field, value, html}`) become `/f/<slug>/thanks-<i+2>`; `None` means no page yet; an invalid rule falls back to the form's own message (`:444-465,963-965`). Words containing `data-pipe` placeholders make the page load the logic script, which fills the answer in with `textContent` (without JavaScript, the words show without the answer) (`:51-54,701-702`).
- **OPS-423** (D-31) **Redirect after sending.** `thanks_redirect` must be an `https://` address of at most 500 printable ASCII characters (`REDIRECT_RE`) (`:219-220,434-441`). The page `/f/<slug>/thanks-go` shows "Taking you on... If nothing happens, continue here" with a `<meta http-equiv="refresh">` and a `no-referrer` meta. The forms service sends people there instead of the other site, "because the site's CSP (form-action 'self') stops a redirect after a POST" (`:707-722`).
- **OPS-424** (D-32) **Places and waitlist pages.** A limit counts only as a whole number from 1 to 10,000 on a choice named `[a-z0-9][a-z0-9_-]{0,59}` of a dropdown, radio or checkbox question, at most 40 per question (`:732-750`). `capacity = {limited, waitlist}` where waitlist needs `limited` (`:753-756`). Both pages are written whenever any choice is limited. `thanks-waitlist` title "You're on the waitlist", text: "You're on the waitlist - we'll be in touch if a place opens." and "Thank you: we've got your answers. The choice you picked is full right now." (`:759-780`). `full` title "That choice has just filled up", text: "Sorry - someone took the last place while you were filling in the form. Nothing was sent." and "Please go back and pick another choice.", with a Back button (`:782-802`). `capacity_cases.json` pins the limits rule to the CRM (`:729`).

## 4. Connections framework (`form-connections.py`, `connections.py`)

- **OPS-433** (D-41) **Design rules.** Connections run on the host, never in the public request, so a slow outside service cannot delay or fail an answer; the answers file stays the single source of truth and everything sent elsewhere is a copy (`tools/form-connections.py:2-10`; `connections.py:1-3`). Each connection is off per form until switched on in the CRM; only answers stored after the switch-on moment are sent (no backlog, except the newsletter, OPS-436); likely spam is never sent; answers held in the CRM are not sent while held. They apply only to forms made in the CRM: rows with `form == "custom"` (`connections.py:177`).
- **OPS-434** (D-42) **Settings file `data/crm/connections.json`, untrusted.** Shape `{"v":1, "written_at", "forms":{<8-char form id>:{"webhook":{...,"since","by"},"notion":{...,"since","by"}}}, "tests":[{"id":<16 hex>,"form","kind","requested_at","by"}]}` (`connections.py:20-25`). Limits: file at most 1 MiB, at most 5,000 forms, at most 50 tests; form id `[a-z0-9]{8}`, connection name `[a-z]{3,20}`, `since` an ISO instant with an offset, `by` trimmed to 80 characters (`:44-54,101-135`). Any entry that fails a check is dropped. Each module re-checks its own fields (URL, database id, secret). The rebuild stores these per form in SQLite and shows the status fields (OPS-438) back in `/admin`.
- **OPS-435** (D-43) **How answer rows are read.** `read_rows` reads `data/submissions.jsonl` by line number from a saved place; lines over 512 KB, broken lines, tombstones, rows whose `form` is not `custom`, rows with a bad `form_id`, and rows with no valid `at` count as lines (so positions stay put) but are not returned (`connections.py:160-183`). Each `Row` carries the CRM's item id (`custom-<12 hex>`), `form_id`, `form_slug`, `form_version`, `at`, `fields`, `spam` (true only when `spam.likely is True`), `repeat_email`, `waitlist`, `source` (`:138-157`).
- **OPS-436** (D-44) **Place, generation, first run.** Each module keeps its own place in `data/forms-connections/<name>rows.json` `{line, gen}` (`connections.py:275,305`). A module's first run starts at the **end** of the file so nothing from before is ever sent, **except** the newsletter, which passes `from_start=True` on its first run because nothing from before the feature can carry that consent (`:266-295`; `conn_newsletter.py:7-8,155`). If the file is shorter than the saved place (lines removed by hand) the module starts again at the new end and bumps `gen`; modules that remember line numbers must forget them when `gen` changes (`connections.py:272-284,297-299`). Order of safety: queue first, `commit` second, so a crash re-reads rows instead of losing them (`:10-12`; `sendqueue.py:229-245`). Settings are read again after the rows so an answer stored just after a switch-on is never judged by older settings (`connections.py:13,212-216,294`).
- **OPS-437** (D-45) **State files.** `data/forms-connections/<name>.json` per module, written by temp file in the same folder, fsync, chmod 0600 and rename (`connections.py:66-83,253-257`). An existing file that is oversized (above 256 MiB), not JSON, or not an object raises `StateUnreadable`, is logged "left as it is, nothing done", and is never overwritten in that run (`:51,186-189,240-257`). The runner records that as `errors[<name>]` (`form-connections.py:63-67`).
- **OPS-438** (D-46) **Status file `data/forms-connections/status.json` (0644).** `{"v":1,"written_at","forms":{<form id>:{<name>:{...}}},"tests":{<test id>:{...,"kind"}},"about":{<name>:{...}},"errors":{<name>:"<exception>"}}` (`connections.py:27-29,312-344`). Values are cleaned: booleans, ints below 10^12, floats rounded to 3 places, strings cut to 300, datetimes to ISO, dicts up to depth 3 and 40 keys, lists up to 20 (`:316-329`). Never secrets or answers. Per-form shapes are in OPS-449, OPS-458, OPS-466. The CRM reads this file; the rebuild's `/admin` shows the same facts (sent, pending, failed, last error, last status, dropped, database title, integration name).
- **OPS-439** (D-47) **Test requests.** The CRM can ask for a test: `ctx.tests_for(name)` returns requests from the last hour for that connection; each module remembers answered test ids for 2 hours and replies `{ok, at, code, last_status}` per id (`connections.py:55,222-224`; `sendqueue.py:219-226`). A test for a form that is switched off answers `code: "off"`; webhook with a bad address `"bad_url"`; Notion without a token `"no_token"`, without a database `"not_found"` (`conn_webhook.py:436-459`; `conn_notion.py:388-404`).
- **OPS-440** (D-48) **Held answers.** `ctx.held(form_id)` reads `data/crm/held.json` (untrusted, OPS-472). Webhook and Notion skip held items while they wait, and drop them quietly (not counted as failed) if they are still held at 48 hours (`connections.py:260-263`; `sendqueue.py:197-207`; `conn_webhook.py:470-471`; `conn_notion.py:423-424`). The newsletter does not check `held`.
- **OPS-441** (D-49) **Time budget.** The runner sets a deadline of 45 s (`form-connections.py:30,52`). Modules check `ctx.time_left()` before each outside call and stop early: webhook needs more than 12 s (`conn_webhook.py:433-434`), Notion more than 11 s (`conn_notion.py:113`), the newsletter 10 s (`conn_newsletter.py:50,203`). The unit's `TimeoutStartSec=120` is the backstop (OPS-398).
- **OPS-442** (D-50) **Dry run.** `--dry-run` reads and plans but never calls an outside service, resolves no DNS, writes no state, no place and no status; it logs counts and ids only, never answers (`conn_webhook.py:49-50,478-481`; `conn_notion.py:47,358-366`; `conn_newsletter.py:206-208`; `connections.py:253-257`).

## 5. `conn_newsletter.py` (Beehiiv)

- **OPS-443** (D-51) **Who is subscribed.** A new custom-form row is queued only if `row.raw["newsletter"] == "yes"`, the row is not likely spam, and `fields.email` is a plain valid address of at most 254 characters (`conn_newsletter.py:54-66,156-161`). The forms service writes top-level `newsletter: "yes"` only when the published form offers the box and exactly one value "yes" was posted (OPS-261, OPS-428). Rows without a usable address are counted as `skipped` and logged. The box is the only consent: there is no pre-ticked box (`newsletter_box.html:3`).
- **OPS-444** (D-52) **The Beehiiv request.** `POST https://api.beehiiv.com/v2/publications/{BEEHIIV_PUBLICATION_ID}/subscriptions`, `Authorization: Bearer <BEEHIIV_API_KEY>`, JSON body `{email, reactivate_existing: true, send_welcome_email: true, double_opt_override: "on", utm_source: "form:<slug>" (or "form"), utm_medium: "website", utm_campaign: "newsletter"}`; timeout 8 s (`conn_newsletter.py:42-43,110-140`). It is the same call as the website newsletter form (OPS-256) with a different `utm_source`. `double_opt_override: "on"` makes Beehiiv send its confirmation email. Key must match 8 to 512 printable ASCII characters, publication id `[A-Za-z0-9_-]{1,80}` (`:52-53,189-191`).
- **OPS-445** (D-53) **Queue and retries.** Each queued address keeps its plain email (so Beehiiv being down never loses a consent), a hash, form id, slug, `tries`, `next`, `first` (`:169-170`). Retry waits: 1, 5, 30 min, 2, 6, 12 h, then every 12 h (`:46,223`). At most 20 Beehiiv calls per run and 5,000 waiting addresses (`:44-45,165-168,203`). A full queue stops reading and re-reads those rows next run (`upto = row.index - 1`). HTTP 429 and 5xx count as "unreachable" (retry); other non-2xx as "rejected" (`:131-138`).
- **OPS-446** (D-54) **Give-up rules.** An address that has waited more than 6 days is dropped and counted in `dropped`; 6 days is deliberately shorter than the 7-day hold before delete-for-good so a deleted answer's address is never added later (`:14-16,47,180-186`). An address Beehiiv refuses with 400, 404 or 422 is dropped after 6 tries (`:49,219-222`). A bad key (401/403) is retried until the 6 days pass (`:219`, test `test_refused_outright_is_dropped_after_a_few_tries_but_a_bad_key_is_kept`).
- **OPS-447** (D-55) **Repeat suppression.** After a successful add the SHA-256 of the lower-cased address is kept for 24 hours (`done`), so several ticks by the same person are added once; the plain address is dropped at that moment (`:48,151-154,210-216`). After 24 hours a new tick adds them again, and `reactivate_existing: true` re-subscribes someone who had unsubscribed (`:10-12`). That is intended: the person ticked again.
- **OPS-448** (D-56) **No key.** Without valid `BEEHIIV_API_KEY`/`BEEHIIV_PUBLICATION_ID` in the job's environment, queued addresses wait, each form's `last_error` becomes `"no_key"`, and a log line says how many are waiting (`:191-195`). Nothing is dropped until the 6 days.
- **OPS-449** (D-57) **Status per form.** `{"sent", "pending", "last_error": "no_key"|"unreachable"|"rejected"|null, "last_error_at", "dropped"?}` (`:23-25,230-239`). `last_error_at` is set the first time a code appears (`:95-99`).
- **OPS-450** (D-58) **Consent gate: what is visible in this part.** FIX-IN-REBUILD context. In Part D the Beehiiv call is gated by an explicit tick on the form itself (`newsletter == "yes"`, OPS-443) and by not being spam. The known bug "Beehiiv sync ignores `email_subscription_consent`" is **not** in this module: it is in the application sync (`tools/intake-newsletter-sync.py`, see OPS-357 and OPS-389), which subscribes on `newsletter == "yes"` alone. The website newsletter form (OPS-256) subscribes even rows labelled likely spam. The rebuild should use one `subscribeIfConsented()` for all three paths and require, for applications, `newsletter == yes` **and** `email_subscription_consent == yes` (OPS-118 makes the second required by the form). Two hazards inside this module are in OPS-521 and OPS-522.

## 6. `conn_webhook.py`

- **OPS-451** (D-59) **Settings per form.** `webhook: {url, secret, since, by}` from `connections.json` (`conn_webhook.py:5-7`). The URL must be `https://`, at most 500 printable ASCII characters, no `#`, no `\`, no userinfo (`@`), no `[]`, no `%` in the host, port absent or 443, a DNS host name with at least two labels, a last label that is letters (2 to 63) or `xn--`, not `localhost`, not ending `.localhost .local .internal .lan .localdomain .home .corp .intranet .private .arpa .invalid .onion .test .example`, not an IP literal (`:73-116`). The secret must be exactly 43 base64url characters (`:74,119-120`). Failing either gives status `bad_url`, sends nothing, and new answers still queue (so fixing it loses nothing) (`:392-406`).
- **OPS-452** (D-60) **The request.** `POST <path>` with `Content-Type: application/json`, `User-Agent: TWC-Forms/1`, `Host`, `Content-Length`, `Connection: close`, plus `X-TWC-Event: answer.created|test`, `X-TWC-Delivery: <32 hex>` (the same on every retry) and `X-TWC-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(key, "<t>.<raw body>")>` (`:13-19,276-281,320-322,355-359`). The key is the secret's 43 ASCII characters as bytes; `t` is the time of that attempt.
- **OPS-453** (D-61) **The body.** `{"event":"answer.created","delivery":"<32 hex>","form":{"id","slug","title"},"answer":{"id":"custom-<12 hex>","at":ISO,"version":int,"source":str,"repeat":bool,"waitlist":bool,"answers":[{"key","label","value":str|[str,...]}]}}`, compact JSON, UTF-8 (`:20-22,325-337`). Only the published form's question keys are sent; a file question's value is the file's name only; a checkbox list is a list of choices (OPS-467). The test event body is `event:"test"`, `test:true`, answer id `custom-000000000000`, source `test`, one answer `{"key":"test","label":"Test","value":"This is a test from TWC Forms. It is not a real answer."}` (`:340-352`).
- **OPS-454** (D-62) **Delivery semantics.** Any 2xx is delivered. Anything else is retried after 1, 5, 30 min, 2, 6, 12 h, then given up as `gave_up` (`sendqueue.py:23,139-145`; `conn_webhook.py:23-24`). At most one delivery in flight per form (forms take turns), at most 30 per run, never past the time budget; a form whose receiver failed in this run gets no more tries in this run (`:431,461-498`). An answer waiting for a retry does not hold back newer ones, so receivers must de-duplicate on `X-TWC-Delivery` and order by `answer.at` (`:26-28`). Nothing waits longer than 48 hours (`sendqueue.py:25,134-136`). At most 1,000 waiting per form and 32 MiB (`:26-27,178-194`).
- **OPS-455** (D-63) **Settings changes.** Switched off: waiting deliveries are dropped and numbers forgotten. New address: waiting deliveries go to the new address with fresh retries and the old error is cleared. New secret: each attempt is signed with the current one. Switched off and on again (new `since`): fresh start and anything queued from before the new `since` is dropped (`:30-34,373-407`). Rows are queued only if `row.at > since` (strictly) and not spam (`:414`).
- **OPS-456** (D-64) **Address safety (runs as root beside private services).** The host name is resolved once per attempt in a thread with a 10 s join; if any resolved address is not plainly public, nothing is sent (`not_allowed`). Blocked: IPv4 `0/8 10/8 100.64/10 127/8 169.254/16 172.16/12 192.0.0/24 192.0.2/24 192.31.196/24 192.52.193/24 192.88.99/24 192.168/16 192.175.48/24 198.18/15 198.51.100/24 203.0.113/24 224/4 240/4`; IPv6 `::/96 ::ffff:0:0/96 ::ffff:0:0:0/96 64:ff9b:1::/48 100::/64 2001::/23 2001:db8::/32 3fff::/20 5f00::/16 fc00::/7 fe80::/10 fec0::/10 ff00::/8`; embedded IPv4 in mapped, 6to4 and NAT64 forms is re-checked; Teredo is always refused; cloud metadata `169.254.169.254` and `fd00:ec2::254`; scoped addresses; the server's own addresses read from `/proc/net/fib_trie` and `/proc/net/if_inet6` (Docker bridges included) (`:36-43,125-247`). The connection goes to exactly the checked address (no second lookup), SNI and `Host` set to the name, certificate verified, TLS 1.2 minimum, no redirects (a 3xx is `rejected`), no proxies, 10 s in total, at most 4 KB of the reply read (`:42-43,250-315`). Error codes: `dns`, `not_allowed`, `timeout`, `tls`, `unreachable`, `rejected` (with status), `bad_url`. The rebuilt sender needs the same SSRF rules; the systemd `IPAddressDeny` (OPS-398) will not exist if it runs inside the app container.
- **OPS-457** (D-65) **Tests.** A test request sends a real signed `test` event, spends one of the run's 30 sends, runs before deliveries ("someone is waiting for them in the CRM"), and stores `{ok, at, code, last_status}` (`:436-459`).
- **OPS-458** (D-66) **Status per form.** `{"ok","sent","pending","failed","last_ok_at","last_error","last_error_at","last_status","dropped"?}` (`sendqueue.py:148-171,210-216`; `conn_webhook.py:501-504`). `ok` is null until the first attempt after a (re)start.

## 7. `conn_notion.py`

- **OPS-459** (D-67) **Settings and credentials.** Per form `notion: {database: "<32 lowercase hex>", since, by}`; the token is `NOTION_TOKEN` from the job's environment (`conn_notion.py:5-8,72,292-294`). Without a token nothing is sent (`no_token`) and new answers wait, given up after 48 hours. Only `https://api.notion.com/v1` is ever called (a fixed host), `Notion-Version: 2022-06-28` (the same as `tools/intake/notion_sync.mjs`), `User-Agent: TWC-Forms/1`, at most 3 requests a second, 10 s timeouts, replies capped at 4 MiB, no proxies or redirects (`:62-66,87-95,109-125`).
- **OPS-460** (D-68) **Database discovery.** The database is read with `GET /databases/{id}` (title and property types, up to 300 properties) and cached 10 minutes; its title shows in the CRM as `database_title` (`:68-69,150-157,368-376`). `GET /users/me` names the connection ("which connection to share the database with"), kept for a day, retried after 10 minutes on failure (`:70-71,381-385`). Result: `about.integration` (`:477-483`).
- **OPS-461** (D-69) **How an answer becomes a page.** One page per answer, created with `POST /pages` (`:467`). Title property: the person's name (a key `name|full_name|fullname|your_name`, else a key containing `name` but not `email` or `user`, else a label `name|your name|full name`), else their email, else `Answer YYYY-MM-DD HH:MM` in New York time (UTC if no tz data) (`:173-195`). Any other property whose name equals a question's label or key (case-folded) is filled when the type fits: `rich_text`; `email` (valid, up to 200); `phone_number`; `url` (`https?://`); `number` (commas stripped, finite); `select` (commas become spaces, up to 100); `multi_select` (up to 100 options); `date` (`YYYY-MM-DD` only); `checkbox` (`yes y on true 1 ticked checked`) (`:206-237,252-264`). A text property named "Answer ID" or "TWC Answer ID" gets the item id (`:74,240-244,256-258`). The page body lists every answer as `Label: value` (each piece at most 2,000 characters, at most 100 blocks, "(More answers than fit here: see the CRM.)" when cut) and ends with `Answer id: <item>` (`:75-76,265-275`). Files: name only, never a link.
- **OPS-462** (D-70) **Never twice, never lost.** `state.pages["<form>:<item>"]` remembers the page made for each answer, at most 20,000 kept (oldest dropped) (`:77,337-338,444-446,451-474`). Before asking Notion to create a page the job saves `maybe_sent = true`. After a crash, timeout or lost connection, the next attempt first queries the database for a page whose "Answer ID" equals the item id and only creates one if none exists. If the database has no "Answer ID" property it creates the page again: "a rare duplicate is better than a lost answer" (`:23-28,456-466`). If Notion answers with a refusal below 500, `maybe_sent` is reset (`:472-473`).
- **OPS-463** (D-71) **Error codes.** `no_token` (none, or Notion 401), `not_shared` (403, 404, or `object_not_found`/`restricted_resource`: the database is not shared with the connection), `not_found` (the id in settings is not a 32-hex id), `unreachable`, `timeout`, `rejected` (other non-2xx; see `last_status`), `gave_up` (an answer failed every retry) (`:30-34,138-145,324-327`). HTTP 429 raises `RateLimited`: the job stops calling Notion for the rest of the run and that try does not count (`:138-140,439-440`). A previous `not_shared`/`no_token` error is cleared once the queue has no attempted item ("shared since") (`:418-419`).
- **OPS-464** (D-72) **Run limits.** At most 20 pages per run; after one failed page the form stops for that run; one item at a time per form (`:67,421-438`). Retry schedule and 48 hours as in OPS-454.
- **OPS-465** (D-73) **Settings changes.** Switched off: waiting answers are dropped. Database changed: waiting answers go to the new database with fresh retries, attempts and `maybe_sent` cleared. Switched off and on again: fresh start (`:35-36,296-319`).
- **OPS-466** (D-74) **Tests and status.** A test only checks that the database can be read; no page is made (`:41,388-404`). Status per form is the common shape plus `database_title` (`:477-483`).

## 8. `sendqueue.py` (shared by webhook and Notion)

- **OPS-467** (D-75) **Turning a stored answer into labelled answers.** Only the **published form's** questions are sent, in the form's order; any other field a request carried (a made-up `status` or `approved`) is never sent, so it cannot fill a Notion property or reach a receiver as if it were an answer. No published form means no answers at all (`sendqueue.py:94-119`). Labels: a field's own `label` when the CRM publishes one (ranking, grid, address), else the question's `data-label` in the published HTML, else the key; consent fields are labelled `Consent`; a link in a label keeps only its words; labels are collapsed and cut to 200 (`:35-84`). Keys match `[a-z][a-z0-9_]{0,39}`, at most 200 answers. A file question sends its stored file name (never a link), with a trailing ` (n KB)` size suffix removed; a checkbox list becomes a list of ticked choices split on `,` (`:30,113-117`). Only string values are sent.
- **OPS-468** (D-76) **Latest labels only.** The published file holds the latest version only, so an answer to an older version gets today's labels for the keys it shares (`:8-10`). The stored `form_version` is passed on but not used to select labels.
- **OPS-469** (D-77) **Retry schedule and limits.** `SCHEDULE = (60, 300, 1800, 7200, 21600, 43200)` seconds; the seventh failure gives up (`attempts > 6`) (`:23,139-145`). `MAX_AGE` 48 hours measured from `queued_at` (`:25,134-136`). `QUEUE_CAP` 1,000 per form and `QUEUE_BYTES` 32 MiB per form; beyond that the oldest waiting answers are given up, counted in `failed` and in `dropped` (`:26-27,178-194`). `expire()` gives up anything older than 48 hours, except held items, which are dropped quietly (`:197-207`).

- **OPS-512** (D-120) **What it does.** Called at the end of every `notify-confirmations.py` run as `main_run(root, dry_run, send, now)`; reads the queue `data/forms-private/resume/*.json` (OPS-496), sends each request from `hello@thewomenscollective.club`, then deletes it (`notify-resume.py:2-9`; `notify-confirmations.py:761-766`). It can also run on its own with `--dry-run` (`:277-282`). If the queue folder is missing or empty it does nothing and does not save state (`:254-261`).
- **OPS-513** (D-121) **The one fixed wording.** Subject: `Your link to finish “<form name>”`. Body: "Hello,", "You asked for a link to finish the form “<form name>” on The Women's Collective website. Open it on any phone or computer to pick up where you left off:", the link, "Your answers are inside the link itself, so anyone who has the link can see them - please don't forward it. It works for 7 days, until <D Month YYYY>.", "Nothing has been sent to us yet: your answers reach us only when you press the button at the end of the form.", "If you didn't ask for this, you can ignore this email.", signature "The Women's Collective / thewomenscollective.club". The only words from outside the file are the form's name (one line, 80 characters, "a form" if empty) (`:83-104`). The date is the link's `exp`, in UTC.
- **OPS-514** (D-122) **Limits and rules.** A form must still offer links (`resume_email: true`) and be open (`open != false`), read from `published/custom/<id>.json` (`:107-126`). A request is deleted unsent if it is over 1 hour old, more than 5 minutes in the future, unreadable, its form no longer offers links, its link is unusable (version, form id, expired), the address is not plain, **the inbox already got a link in the last 24 hours** (whatever the form), **20 links a day to one domain** (not for the 24 big providers: `gmail.com outlook.com hotmail.com live.com msn.com yahoo.com ymail.com icloud.com me.com mac.com aol.com proton.me protonmail.com gmx.com fastmail.com hey.com yahoo.co.uk hotmail.co.uk outlook.co.uk comcast.net verizon.net att.net zoho.com`) or one visitor already asked for 3 this hour (`:46-56,146-184`). Caps: 10 per run, 30 per hour, 200 per day; what is left waits (`:47,185-188`). Half-written `*.tmp` files older than 10 minutes are swept (`:50,235-249`).
- **OPS-515** (D-123) **At most once.** The address, domain and visitor are recorded and the state saved **before** the send; the request is deleted whatever the result, so a failure is never retried and the person is never told either way (`:194-207`). Logs never contain an address or an answer, only form ids (`:24`).
- **OPS-516** (D-124) **State `data/notify_resume_state.json` (0600).** `{"version":2,"addresses":{<hmac>:ISO},"domains":{<hmac>:[ISO]},"visitors":{<hmac>:[ISO]},"sent_at":[ISO]}`, pruned to 24 h / 24 h / 1 h / 24 h (`:71-72,138-143,213-225`). The forms service reads `addresses` (read-only) to drop repeats at request time (OPS-496).
- **OPS-517** (D-125) **The link points at the apex.** `SITE = "https://thewomenscollective.club"` and the link is `SITE/f/<slug>#resume=<payload>` (`:44,190`). See OPS-518.

## 17. Surprises, bugs and risks

- **OPS-518** (D-126) **Hard-coded apex URL in links people already hold.** `custom_pages.py:58` (`SITE`), `notify-resume.py:44` and the finish-later emails (OPS-513), thank-you and embed pages, and every canonical/og URL point at `https://thewomenscollective.club/f/<slug>`. After cutover the apex shows only coming-soon (BRIEF decision 1), and `/f/*` is not in the owner's archive-and-redirect list (BRIEF decision 3). **The live `/f/<slug>` forms, their `/thanks`, `/event.ics`, `/forms` and `/f/media/*` URLs must resolve on the new app or 301 to it**, and resume links already sitting in inboxes (7-day lifetime) must keep working. Decide where `/f/*` lives before stopping the old timers.
- **OPS-519** (D-127) **External origins that the new CSP does not allow.** The old pages load Google Fonts stylesheets for four font sets (`custom_pages.py:222-233`), Cloudflare Turnstile (`challenges.cloudflare.com`) (`apply_site_forms.py:69`; `formguard.py:30-32`) and send people to `https://calendar.google.com` (a link, not a load) (`custom_pages.py:1198-1202`). The new app serves a same-origin-only CSP (AGENTS.md: "a new external origin goes there, with a test"). Self-host the fonts (as the scrapbook kit already does) and add the Turnstile origins with a test, or drop the look font sets that need an outside stylesheet.
- **OPS-520** (D-128) **The consent-bug cross-reference (Beehiiv).** FIX-IN-REBUILD. See OPS-450. The Part D newsletter path is the correct pattern (explicit tick on the form, not spam); the application path ignores `email_subscription_consent` (OPS-357, OPS-389) and the site newsletter form subscribes likely spam (OPS-256).
- **OPS-521** (D-129) **State loss re-subscribes people who unsubscribed.** FIX-IN-REBUILD. The newsletter module starts from the **beginning** of `submissions.jsonl` whenever its place file `data/forms-connections/newsletterrows.json` is missing (`connections.py:278-288`; `conn_newsletter.py:155`), and the dedup hashes are kept only 24 hours (`:48,151-154`). Losing or deleting that one file (or a restore from an older backup, OPS-390) re-queues every person who ever ticked the box, and `reactivate_existing: true` re-activates those who had unsubscribed in Beehiiv (`:115`). The rebuild should record a per-address "subscribed at" in SQLite and never re-send consent from a replayed row.
- **OPS-522** (D-130) **A spam label silently removes a real opt-in.** `conn_newsletter.py:156` skips any row with `spam.likely`, and webhook/Notion do the same (`conn_webhook.py:414`; `conn_notion.py:335`). A genuine person caught by the heuristics (for instance the 3-second "too fast" rule, OPS-484) never reaches Beehiiv, the webhook or Notion, and nothing tells the CRM user. The rebuild should expose "not sent: labelled spam" and let an admin release it.
- **OPS-523** (D-131) **Refusals do not fail the unit.** FIX-IN-REBUILD. `apply_site_forms.py` and `custom_pages.py` print refusals to stderr and exit 0 (`apply_site_forms.py:393-399,425`; `custom_pages.py:600-601`); `form-connections.py` exits 0 even when a module raised (`form-connections.py:63-70`). Nobody learns that a form was not applied unless they read the journal. The rebuild should surface publish and connection errors in `/admin` (the connections status already models this, OPS-438).
- **OPS-524** (D-132) **A failed confirmation burns the address for a day.** `notify-confirmations.py` writes the address hash before it sends (`:451,512`) and never removes it when the send fails (`:361-365`). One Cloudflare outage means the person gets no confirmation, is never retried, and any further answer from them within 24 hours is skipped as `per_address`. The same applies to finish-later requests (`notify-resume.py:195,205-207`). The rebuild should retry transient failures with a cap and only mark the address on success.
- **OPS-525** (D-133) **Counting responses depends on the writer's JSON spacing.** `apply_site_forms.count_responses` finds a form's rows by the literal `"form": "<kind>"` (`apply_site_forms.py:233`), which holds only while `submissions.py` writes `json.dumps(..., ensure_ascii=False)` with default separators (`submissions.py:200`). The rebuild must count from a column, not from text.
- **OPS-526** (D-134) **The form-started stamp is unsigned, and omitting it means no penalty.** `FORMS_STAMP_SECRET` is never set (OPS-487), and a request without `form-started` is treated as "unknown" (`spamcheck.py:164-165,269-280`). The "too fast" rule therefore catches only bots that include the stamp. If the rebuild keeps the rule, sign the stamp and treat a missing one as a mild signal.
- **OPS-527** (D-135) **Two pitch detectors disagree.** `spamcheck.check` matches whole words (`:70-72`), while `looks_like_pitch` and `notify_settings.looks_like_pitch` use plain substrings (`spamcheck.py:37-39`; `notify_settings.py:69-71`), so "Seoul" or "geology" can be flagged "(looks like a sales pitch)" in alerts and can suppress a confirmation when a record has no stored verdict. Use one function.
- **OPS-528** (D-136) **Unsalted address hashes.** Confirmations store `sha256(lower(email))[:20]` (`notify-confirmations.py:296-298`), the newsletter `sha256(lower(email))` (`conn_newsletter.py:58-59`); both are guessable for a known address. The finish-later job does it properly with HMAC and a key (OPS-497). Use the keyed form in the rebuild.
- **OPS-529** (D-137) **Rate limits live in memory.** The per-visitor form limit, the beacon limit and the resume limits are in-process and reset on every restart (`formguard.py:18-20`; `funnel.py:322-345`; `resumelink.py:58-61`), and the Cloudflare range list is a hard-coded copy "checked 2026-10-29" (`formguard.py:53-61`). The new app already limits applications and contact by IP (AGENTS.md); custom forms, beacons and resume need the same, with Cloudflare's header trusted only from Cloudflare's ranges.
- **OPS-530** (D-138) **Webhook and Notion deliveries are lossy after 48 hours or 7 attempts.** After the sixth retry or 48 hours the answer is "gave up", counted and gone from the queue (`sendqueue.py:25,139-145,197-207`). The source row remains in `submissions.jsonl`, but nothing offers a way to resend; a CRM user can only see the failed count. The rebuild should keep the failed delivery rows and offer a manual resend.
- **OPS-531** (D-139) **First-run asymmetry.** Webhook and Notion start at the end of the file and send nothing from before (`connections.py:289-292`), and each also ignores rows at or before the form's `since` (`conn_webhook.py:414`; `conn_notion.py:335`). The newsletter alone reads from the start (OPS-436). The rebuild's import (BRIEF decision 10) must not replay the 128 applications, the 120 members, the 44 newsletter subscribers or old custom-form answers through any of these paths.
- **OPS-532** (D-140) **Notion mapping depends on the person naming properties like questions.** A property gets an answer only if its name equals a question's key or label after case-folding; types that do not fit are silently skipped (`conn_notion.py:259-264`). Without a text property named "Answer ID" a retry after a crash can create a duplicate page (OPS-462). The CRM's setup steps suggest adding that property; the rebuild's settings screen must say so too.
- **OPS-533** (D-141) **Sender account.** All of Part D's emails go through the Cloudflare Email Sending code in `notify-applications.py` using `/opt/nbwc/.cf-email-sending.json` (OPS-363, OPS-392). The new app sends everything through `sendEmail()` (AGENTS.md); the confirmation and finish-later emails need `from = hello@thewomenscollective.club`, an attachment (`event.ics`) and the 10 per run / 30 per hour / 24 h-per-address caps preserved.
- **OPS-534** (D-142) **Secrets and files named in this part.** Env names only: `BEEHIIV_API_KEY`, `BEEHIIV_PUBLICATION_ID`, `NOTION_TOKEN`, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `CRM_TURNSTILE_SITE_KEY`, `FORMS_STAMP_SECRET` (never set), `TWC_FORMS_LIB`, `FORMS_PRIVATE_DIR`, `FORMS_STATS_DIR`, `FORMS_STATS_FLUSH_SECONDS`, `FORMS_HELD_FILE`, `FORMS_DELETIONS_FILE`, `FORMS_DELETIONS_STATUS`, `UPLOADS_DIR`, `NOTIFY_RESUME_STATE`. Files with secrets: `/opt/nbwc/.env` (loaded by `twc-form-connections.service` only), `/opt/nbwc/.cf-email-sending.json`, `data/forms-private/resume-key` (64 hex, a keyed-hash secret), webhook signing secrets inside `data/crm/connections.json` (43 base64url characters each, `<redacted>`), and webhook/Notion queues in `data/forms-connections/*.json` that hold **answer text and plain email addresses** (0600) (`conn_webhook.py:417-419`; `conn_newsletter.py:169-170`). Backups (`tools/backup-data.py`, OPS-370) must treat these as sensitive.
