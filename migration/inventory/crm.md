# CRM inventory: legacy CRM (`crm/`) — auth, inbox, application review, member links, forms, notifications, connections

Source: code snapshot `legacy/crm/` plus `legacy/compose.yaml` and `legacy/Caddyfile` (no real data; made-up samples in `legacy/testdata/`). Generated 2026-11-09.
Each `CRM-nnn` item is one behaviour that must survive the move into `/admin`, or one risk to fix instead of port. Citations are `file:line`
relative to `legacy/` (the CRM's own files are `crm/server/…`, `crm/shared/…`, `crm/src/…`, `crm/src-v2/…`). Environment variables are named
but never valued. The bracket at the end of an item is the migration workstream from `migration/BRIEF.md` (`owner`), or `retired`.
Where an item names `OPS-nnn` it points at `migration/inventory/backoffice.md` (the intake / forms services the CRM drives).
`backoffice.md` already lists the CRM's routes at a high level (OPS-280–OPS-286); this file is the per-behaviour inventory and the one the manifest should use for the CRM.

**Item count: 188** (CRM-001 to CRM-188).

**Live UI default: Classic.** One Node server serves Classic (`crm/src/`) at `/` and Bento (`crm/src-v2/`) at `/v2`, on the same `/api/*`.
A person's saved theme decides which one the plain address opens (default `classic`); see CRM-020, CRM-163, CRM-164.

## Gaps (read these before signing off)

1. **Host jobs behind the CRM's settings files are Part D in `backoffice.md` and still unread**: `tools/forms/apply_site_forms.py`, `conn_notion.py`, `conn_webhook.py`, `conn_newsletter.py`, `formguard.py`, `resumelink.py`, `tools/form-connections.py`, `tools/notify-confirmations.py`, `tools/notify-resume.py`, `tools/notify-messages.py`, `tools/notify-applications.py`. The CRM only writes JSON files for them (CRM-011, CRM-139, CRM-144); what they send, when and with which template is outside this inventory.
2. **The custom-form engine is itemised by capability** (CRM-117–CRM-127), not per question type, logic rule or look token. The `custom-forms` workstream needs its own per-feature read of `shared/formlogic.ts`, `formdef.ts`, `composite.ts`, `look.ts`, `customconfirm.ts` and `editor/*.tsx` before it can be marked parity.
3. **Classic vs Bento** were compared by API surface and file list (identical, CRM-164); a screen-by-screen visual diff was not done. Treat them as one capability.
4. **There is no CRM-wide CSV export.** The only CSV in the CRM is per custom form (CRM-130). Application and member CSVs live in the legacy intake admin (OPS-037), not here.
5. **Spam heuristics are not in the CRM.** It mirrors the verdict the forms service and intake wrote (CRM-047); the rules are in `tools/forms/spamcheck.py` (Part D) and `intake/spam_hook.py` (OPS-058–068).
6. **No global Notion / Beehiiv / webhook settings exist in the CRM.** Connections are per custom form (CRM-144–CRM-155); Beehiiv for applications and the site newsletter form is done by host tools (CRM-154, CRM-182).

## 1. Auth modes, sessions, sign-in page

- **CRM-013** **Three auth modes** chosen by `CRM_AUTH_MODE`: `caddy` (default), `access`, `password` (`crm/server/config.ts:24-27`; `crm/server/index.ts:43-52`). Production uses `password` (`Caddyfile:409-411`); compose still defaults to `caddy` (`compose.yaml:84`). The rebuild uses Better Auth (AGENTS.md); none of the three is ported. [retired]
- **CRM-014** **Named users, no roles**: `CRM_USERS` = `id:Name[:email]`, default `natasa:Natasa,teddy:Teddy`; the lower-cased id is what history records (`actor`). Every signed-in person can do everything, including approve, decline, publish, delete-for-good, secrets (`crm/server/auth.ts:13-20`; `crm/server/config.ts:34`; `crm/server/responsesroutes.ts:21-26`). Rebuild: map to two admin members; keep `actor` on every event. [admin-inbox]
- **CRM-015** **`caddy` mode trusts `X-Auth-User`** set by a reverse proxy's basic auth (`crm/server/auth.ts:24-27`). Safe only because Caddy deletes the visitor's copy (CRM-005). [retired]
- **CRM-016** **`access` mode** verifies the Cloudflare Access JWT (`cf-access-jwt-assertion`) with `jose`: signature, issuer `https://<team>`, audience, then matches the email to a user; refuses to start without `CRM_ACCESS_TEAM_DOMAIN`, `CRM_ACCESS_AUD` and an email for every user (`crm/server/auth.ts:34-48`; `crm/server/index.ts:44-46`). Kept only for rollback. [retired]
- **CRM-017** **`password` mode credentials**: per-user `salt:hash` (scrypt N=16384 r=8 p=1, 32 bytes, base64url, no `$`), parsed from `CRM_PASSWORD_HASHES`; malformed entries skipped; scrypt always runs (dummy salt for an unknown name) and compares in constant time. User names are case-insensitive and trimmed (phones capitalise); passwords are trimmed (`crm/server/auth.ts:52-70,95-109`). [admin-inbox]
- **CRM-018** **Session cookie** `twc_crm_session`: `base64url(JSON{u,exp,k}).HMAC-SHA256`, 14 days, `HttpOnly; Secure; SameSite=Lax; Path=/`. `k` fingerprints the user's current password hash, so changing a password signs that person out everywhere. `CRM_SESSION_SECRET` must be ≥ 32 characters or the server throws (`crm/server/auth.ts:72-126`; `crm/server/index.ts:110`). [admin-inbox]
- **CRM-019** **Sign-in page**: server-rendered (works before the app loads) `GET /login` + `GET /login.js` + `POST /login`; already-signed-in visitors are redirected to `next`; `safeNext` allows only same-site paths and never `/login`, `//…` or `/\…`; optional note line (`CRM_LOGIN_NOTE`); failures log the attempted name (capped) and never the password (`crm/server/index.ts:107-155`; `crm/server/loginpage.ts:6-8`). Login CSRF: `Sec-Fetch-Site` must be `same-origin`/`none`, else `Origin` must match the host (`Origin: null` allowed because the site's `Referrer-Policy: no-referrer` makes browsers send it) (`crm/server/index.ts:120-135`). [admin-inbox]
- **CRM-020** **Sign-in throttle**: 10 failures per client address per 15 minutes → HTTP 429 "Too many tries. Wait 15 minutes"; success clears. Client address = last `X-Forwarded-For` entry; if that falls in a built-in list of Cloudflare ranges (IPv4 and IPv6), `CF-Connecting-IP` is used instead, and a forged one from a non-Cloudflare peer is ignored (`crm/server/auth.ts:129-175`; `crm/server/index.ts:141-153`). [admin-inbox]
- **CRM-021** **API gate**: every `/api/*` call needs a known user (401 JSON); every non-GET also needs header `x-crm: 1` (403) — the server grants no CORS so a cross-site form can't forge writes; every response is `Cache-Control: no-store` (`crm/server/index.ts:157-167`). The client sends `x-crm: 1` on every request and bounces to `/login?next=` on a 401 (`crm/src/api.ts:15-27`). Rebuild: use `src/start.ts` CSRF middleware instead. [admin-inbox]
- **CRM-022** **Page gate**: in password mode any non-API GET by a signed-out visitor is a 303 to `/login?next=<path+query>`; `POST /api/logout` clears the cookie; `GET /api/me` returns `{user, name, canSignOut, theme}`; `GET /api/users` lists `{id,name}` (`crm/server/index.ts:169-176,183-188,520-524`). [admin-inbox]
- **CRM-023** **Per-person preference `theme`** (`classic` | `bento`) in table `user_prefs`; `PUT /api/prefs/theme`; invalid value → 400 "Choose classic or bento" (`crm/server/prefs.ts:5-25`; `crm/server/index.ts:177-182`). Only this one preference exists. [admin-inbox]

## 17. Known bugs and risks

Tags: **FIX-IN-REBUILD** = do not port, reproduce the intended behaviour correctly; **RETIRE** = drop; **PORT-WITH-CARE** = port, with the named guard.

- **CRM-171** **FIX-IN-REBUILD — plaintext review-link tokens (intake-side, not CRM-side)**: `staging_links.txt` holds full member review URLs including raw tokens (mode 600; the admin appends, `make_links.py issue` overwrites), defeating the hashed-token design if the data dir leaks or is backed up (`intake/intake.py:853-860`; `intake/make_links.py:7,26,93-97`; OPS-087, OPS-051). **The CRM itself never stores the URL** (CRM-082: history keeps `link_id`, purpose, expiry only). Rebuild: store only a token hash, show the URL once, no file of live links. [members-links]
- **CRM-172** **FIX-IN-REBUILD — wrong or missing record when `record_id` is absent**: the CRM's application id is `app-<record_id>` or, with no `record_id`, `app-<hash(at|email)>` (`crm/server/ingest.ts:191`); `decide()` sends `itemId.slice(4)` as `record_id` (`crm/server/decisions.ts:46`), a hash the intake has no record for, so approve / decline answer 404 "doesn't know this application" (`:54`; intake `_application_by_id` matches only an equal `record_id`, `intake/intake.py:2034-2035`). The intake dashboard has the mirror problem: its `new:<index>` key counts position in a newest-first list, so approve / archive can land on a different record after the list changes (`intake/intake.py:1812-1813,2141-2142,2255-2258`; OPS-083). Rebuild: every application gets a permanent UUID at import and at submission; approve, decline, archive use that id only; import backfills missing `record_id`s. [admin-inbox]
- **CRM-173** **FIX-IN-REBUILD — item id collisions**: contact / partnership / newsletter ids are `sha256(at|form|email)[:12]` and custom ids `sha256(at|form_id|email)[:12]`; two submissions with the same timestamp string and email collapse into one item (`seen` skips the second) and 48 bits is thin for a large import (`crm/server/ingest.ts:126-127,244,356-359`; `crm/server/customingest.ts:20-26`). - **CRM-176** **FIX-IN-REBUILD — read-modify-write without locks on shared JSON**: the CRM rewrites `forms_state.json`, `notify_settings.json` and `connections.json` as read-then-write with atomic rename but no lock between two simultaneous writers (two people saving in the same moment: last write silently wins) (`crm/server/forms.ts:156-176`; `crm/server/notify.ts:161-215`); intake has the same pattern on its JSONL (OPS-088; the forms service, by contrast, serialises appends behind a lock, OPS-224).
